# Phase 1 — Requirements Compliance Report
## Result: NON-COMPLIANT
### Summary
Most functional requirements are implemented (search, category filter, price filters, combined filters, single product endpoint). However the error payload for the minPrice > maxPrice case (REQ-03) does not match the required JSON error string (camelCase). There are also inconsistent error message formats for invalid numeric price inputs.
### Missing requirements
- REQ-03: Exact error JSON for minPrice > maxPrice — requirements expect { "error": "minPrice cannot be greater than maxPrice" } but code returns a different string.
### Errors found
- techshop_testing/Server.py — in get_products() (diff hunk @@ -137,23 +137,23 @@): the code returns jsonify({"error": "min price cannot be greater than max price"}), 400 instead of the required jsonify({"error": "minPrice cannot be greater than maxPrice"}), 400.
- techshop_testing/Server.py — in get_products() (minPrice parsing block): returns jsonify({"error": "min price must be a number"}), 400. Requirement did not mandate the exact message for parsing errors, but the message uses 'min price' (space, lower-case) rather than the camelCase 'minPrice' used elsewhere in the API and in the requirements; this is an inconsistency.
- techshop_testing/Server.py — in get_products() (maxPrice parsing block): returns jsonify({"error": "max price must be a number"}), 400, using 'max price' instead of 'maxPrice' which is inconsistent with requirement naming convention.
### Suggestions
- In techshop_testing/Server.py, update the min/max price validation error messages to use the camelCase names required by the spec. Specifically: change return jsonify({"error": "min price cannot be greater than max price"}), 400 to return jsonify({"error": "minPrice cannot be greater than maxPrice"}), 400. This addresses REQ-03's explicit required error payload.
- Standardize parsing error messages to use camelCase parameter names to avoid confusion. For example change return jsonify({"error": "min price must be a number"}), 400 to return jsonify({"error": "minPrice must be a number"}), 400 and similarly change 'max price must be a number' to 'maxPrice must be a number'.
- Run the automated tests (if any) or add a unit/integration test asserting the exact error JSON for the minPrice>maxPrice case: GET /api/products?minPrice=200&maxPrice=100 should return 400 and {"error": "minPrice cannot be greater than maxPrice"}.
### Quality notes
- Overall implementation is clear and readable: filters are applied stepwise (category, search, price) and combined correctly.
- Search handling correctly treats whitespace-only search terms as no-op and uses case-insensitive substring matching as required.
- Price parsing properly rejects NaN and infinity via math.isnan/isinf, which is a good defensive check.
- There is inconsistency in error message casing/format (e.g., 'min price' vs 'minPrice') — use consistent parameter naming (camelCase) across all error payloads to match the requirements and improve API ergonomics.
- Two separate @app.after_request functions are defined (set_session_cookie and add_cors_headers). Flask supports multiple after_request handlers, but consider combining or documenting ordering if side effects depend on order.
- Minor typos in comments (e.g., 'Helath') — not functionally harmful but worth cleaning up.
