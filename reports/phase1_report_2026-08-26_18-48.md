# Phase 1 — Requirements Compliance Report
## Result: NON-COMPLIANT
### Summary
Most requirements are implemented (search, category filter, price-range filtering, combined filters, single product endpoint). However, numeric validation for price parameters is incomplete: the code no longer rejects non-finite numbers (NaN/Infinity) and thus can return 200 with an empty result instead of a 4xx error for invalid numeric inputs. Also input normalization for category does not trim whitespace.
### Missing requirements
- REQ-03 (robust invalid-number handling): Reject non-finite numeric inputs (NaN/Infinity) for minPrice and maxPrice with 4xx, as required by the acceptance rule that invalid inputs produce appropriate 4xx codes.
### Errors found
- techshop_testing/Server.py: The import of the math module was removed (diff hunk @@ -2,7 +2,7 @@) but the previously-intended checks for non-finite floats were also removed. In the get_products() function (diff hunk @@ -135,29 +135,25 @@), the lines that would have raised ValueError for math.isnan(...) / math.isinf(...) were deleted (see removed lines:
-          if math.isnan(min_price) or math.isinf(min_price):   # ← add this line
-            raise ValueError
and similarly for max_price). As a result, passing minPrice=NaN or maxPrice=Infinity will not cause a 400 response; float('NaN') / float('inf') succeed and later comparisons silently fail/behave unexpectedly.
- techshop_testing/Server.py: Category normalization uses category = category.lower() but does not strip surrounding whitespace. A category value like ' electronics' (leading/trailing spaces) will become ' electronics' and be treated as invalid, returning 400. This is likely an input-normalization bug (diff hunk @@ -114,20 +114,20 @@ shows the lowercasing change).
### Suggestions
- Reintroduce validation for non-finite numbers in get_products():
- Re-add import math at top of techshop_testing/Server.py (restore 'import math').
- After converting min_price = float(min_price_raw) and max_price = float(max_price_raw), verify they are finite. Use math.isfinite(value) (preferred) or check not (math.isnan(value) or math.isinf(value)). If not finite, return 400 with an error like {"error": "minPrice must be a finite number"} or {"error": "maxPrice must be a finite number"}.
 Example fix around the existing try/except blocks:
 try:
     min_price = float(min_price_raw)
     if not math.isfinite(min_price):
         raise ValueError
 except ValueError:
     return jsonify({"error": "minPrice must be a number"}), 400
(and same for max_price)
This restores the originally-intended behavior present in the earlier diff comments and ensures invalid numeric inputs yield 4xx as required.
- Trim category input before lowercasing to be more tolerant of whitespace: replace
 category = category.lower()
with
 category = category.strip().lower()
This avoids returning a 400 for otherwise valid category values that include accidental spaces.
- Optional: combine the two @app.after_request handlers (set_session_cookie and add_cors_headers) or ensure their execution order is intentional. This is not required by the feature, but reduces surprising side effects and keeps response header logic in one place.
### Quality notes
- The code is generally clear and structured: get_products() applies filters in a sensible order (category -> search -> price), and uses early returns for invalid inputs.
- Search handling correctly treats whitespace-only or empty search terms as 'no filter' by using .strip() and checking for truthiness — this matches REQ-01.
- Category validation correctly enforces allowed categories ('electronics' and 'accessories') and is case-insensitive. Adding .strip() as suggested will make it more robust.
- Price range comparison and the minPrice>maxPrice error are implemented correctly. The only gap is missing detection of non-finite floats (NaN/Infinity).
- Minor: two separate @app.after_request decorations are used (set_session_cookie and add_cors_headers). Flask supports multiple after_request handlers, but consolidating them can simplify the response-processing flow.
