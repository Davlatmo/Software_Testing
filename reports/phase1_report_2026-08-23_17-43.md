# Phase 1 — Requirements Compliance Report
## Result: NON-COMPLIANT
### Summary
The implemented endpoints largely cover the required functionality (search, category filter, price range, combined filters, and single-product retrieval). However there are a few deviations and missing validations: the category validation allows an extra 'all' value not specified in the requirements, category matching is case-sensitive, and numeric query parameters (minPrice/maxPrice) lack explicit validation when conversion fails — which means invalid numeric input is silently ignored instead of returning a 4xx. These issues cause the implementation to not fully meet the acceptance criteria about invalid inputs and exact valid categories.
### Missing requirements
- REQ-02: Strict category validation limited to only the declared valid values ('electronics', 'accessories'); the code also accepts 'all' which is not listed in requirements.
- Acceptance criteria: Return appropriate 4xx for invalid numeric inputs (e.g., non-numeric minPrice/maxPrice). The code silently treats bad numeric inputs as None.
### Errors found
- techshop_testing/Server.py — get_products (hunk @@ -109,29 +109,38): VALID_CATEGORIES includes 'all' (line: +    VALID_CATEGORIES = {"electronics", "accessories", "all"}). The requirements only list 'electronics' and 'accessories' as valid categories. Allowing 'all' deviates from REQ-02.
- techshop_testing/Server.py — get_products (same hunk): category comparison and validation are case-sensitive (code checks membership and equality using the raw 'category' query param). If clients send 'Electronics' or 'ELECTRONICS' it will be treated as invalid or not matched, while requirements do not specify case-sensitivity—this is likely unexpected and brittle.
- techshop_testing/Server.py — get_products (hunk @@ -109,29 +109,38): minPrice and maxPrice use request.args.get(..., type=float). If a caller provides a non-numeric value (e.g., minPrice=abc), Flask's type converter will return None rather than a 4xx response, causing the endpoint to silently ignore the invalid parameter instead of returning an appropriate 4xx as required by the acceptance criteria.
- techshop_testing/Server.py — get_products docstring: it claims to 'Implements REQ-01, REQ-02, REQ-03, REQ-04, REQ-05' though REQ-05 is the single-product endpoint; this is a minor documentation mismatch (hunk near @@ -109,29 +109,38).
### Suggestions
- Remove 'all' from VALID_CATEGORIES so validation matches the requirements exactly. Change the line in techshop_testing/Server.py (get_products) from: VALID_CATEGORIES = {"electronics", "accessories", "all"} to: VALID_CATEGORIES = {"electronics", "accessories"}. If you intend to support an 'all' shorthand, document it in the requirements or treat it as an alias on the client side (not as a change to valid categories).
- Normalize category query param to lowercase before validation and comparison so matching is case-insensitive. For example, in get_products (techshop_testing/Server.py) do: if category: category = category.lower(); then validate and filter using the lowercased value. Update the membership check and the product category comparison to use the normalized value.
- Explicitly validate numeric query parameters and return 400 on invalid numbers. Instead of relying solely on request.args.get(..., type=float), parse and detect conversion errors and return a 400 with a helpful error payload. Example fix in get_products (techshop_testing/Server.py):
- Attempt to parse minPrice and maxPrice from request.args.get without type=float, catch ValueError, and return jsonify({"error": "minPrice/maxPrice must be numeric"}), 400 for invalid input.
- Alternatively, after using type=float, detect when the raw query param exists but the parsed value is None and return 400 indicating an invalid number.
- Fix the docstring in get_products to avoid claiming it implements REQ-05 (single product endpoint) — update or remove the misleading line near the top of the function in techshop_testing/Server.py.
### Quality notes
- Good: The search implementation strips whitespace and performs a case-insensitive substring match (search.strip() then lower()), which satisfies REQ-01 behavior for empty/whitespace searches.
- Good: Price filtering uses inclusive comparison (>= and <=), matching REQ-03.
- Good: Combined filters are performed by sequentially narrowing the 'filtered' list, so filters interact correctly per REQ-04.
- Concern: Using Flask's request.args.get(..., type=float) is convenient but hides conversion failures; explicit validation would make error handling clearer and match the acceptance criteria for invalid inputs.
- Minor: Several docstring formatting changes were made; keep docstrings concise and accurate to avoid confusion about which function implements which requirement.
